# SENTINEL — AI-Powered Insider Threat Detection & Behavioural Monitoring

An academic demonstration of how a banking organisation can detect insider
threat from the telemetry its own applications already produce. Sentinel is not
a CRUD application with a security theme bolted on: the point of the project is
the pipeline, and everything else exists to feed it.

```
Employee action
   → security telemetry          (activities)
   → behavioural baseline        (employee_baselines — what is normal for THIS person)
   → 11 deterministic rules  ┐
   → Isolation Forest        ├─→ risk engine (0–100, 5 bands, decayed)
   → baseline deviation      ┘
   → threat alert                (anomalies — one incident, one queue entry)
   → analyst investigation       (audit_logs — append-only)
```

## What is real and what is simulated

Stated plainly, because a security demonstration that overstates itself is
worthless:

| Element | Status |
| --- | --- |
| Telemetry, baselines, rules, ML, risk, alerts, audit | **Real.** Implemented and exercised by the test suite. |
| Banking data (customers, accounts, transactions, loans, documents) | **Synthetic.** Generated by `app/utils/seed_banking.py`. Never real customer information. |
| USB activity | **Simulated.** No endpoint surveillance is performed or possible. |
| Location | **Approximate city/country**, as recorded on the event. No GPS, no precise tracking, no invasive monitoring. |
| Security-console UI | **Partially wired.** The employee portal and login are live. The six original console views still render from `src/data/mock.ts` and are being migrated to the API. |

## Stack

| Layer | Choice |
| --- | --- |
| API | FastAPI, SQLAlchemy 2.x, Alembic, Pydantic v2 |
| Database | PostgreSQL (application), SQLite (tests) |
| Auth | JWT (HS256) via python-jose, bcrypt via passlib |
| ML | scikit-learn `IsolationForest`, NumPy, pandas |
| UI | React 19 + TypeScript, Vite, Tailwind CSS v4, Recharts 3 |

## Running it

**Backend**

```bash
cd backend
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env          # then edit DATABASE_URL and JWT_SECRET
alembic upgrade head
python -m app.utils.seed      # roles + the demonstration employees and analysts

uvicorn app.main:app --reload          # http://localhost:8000/docs
```

On startup the API seeds the synthetic bank (branches, customers, accounts,
transactions, loans, documents) and the classified resource registry. Both are
idempotent and skip silently if the data is already present.

The financial history is only half the picture — detection also needs
*behavioural* history to learn from. With no telemetry there is no baseline to
derive and nothing for the Isolation Forest to train on, so a fresh install
scores everything as LOW until you generate it:

```bash
# as a SECURITY_ANALYST, once, on an empty database
curl -X POST localhost:8000/api/v1/admin/demo/history?days=30 \
     -H "Authorization: Bearer $TOKEN"
```

That writes 30 days of ordinary working activity, recomputes every baseline,
and trains the model. It refuses to run twice unless you pass `force=true`.

**Frontend**

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # tsc -b && vite build
npm run lint     # oxlint
```

**Tests**

```bash
cd backend && venv/bin/python -m pytest tests/ -q
```

The suite runs against SQLite in a throwaway file, not PostgreSQL, so it needs
no running database. It is not a subset of the application's behaviour: the
detection pipeline is tested by driving real events through the real rule
engine and the real risk scorer.

## The demonstration

The eight scenarios from the specification are runnable from the console or the
API:

```bash
curl -X POST localhost:8000/api/v1/admin/demo/scenario/combined_insider \
     -H "Authorization: Bearer $TOKEN"
```

| Scenario | What it does | Expected |
| --- | --- | --- |
| `normal` | An ordinary working day | No alert |
| `after_hours` | Sensitive access at 02:00 | RULE-007 |
| `new_device` | Login from an unrecognised workstation | RULE-003 |
| `unusual_location` | Access from an unseen city | RULE-001, RULE-010 |
| `mass_lookup` | Sweep of the customer book | RULE-004, RULE-005 |
| `sensitive_download` | Repeated CONFIDENTIAL downloads | RULE-006, RULE-008 |
| `usb_transfer` | RESTRICTED file copied to removable media | RULE-009 |
| `combined_insider` | Reconnaissance → enumeration → collection → exfiltration | CRITICAL |

Each scenario returns its own score progression, step by step, so the escalation
is visible rather than asserted. See `docs/demo.md`.

## Roles

| Role | Portal |
| --- | --- |
| `TELLER`, `RELATIONSHIP_MANAGER`, `BRANCH_MANAGER`, `COMPLIANCE_OFFICER`, `OPERATIONS_MANAGER` | Employee banking portal. These identities are the *subjects* of monitoring. |
| `ADMIN`, `SECURITY_MANAGER`, `SECURITY_ANALYST` | Security console. These identities *do* the monitoring. |
| `VIEWER` | Read-only security access. |

The two groups are disjoint in both directions. An employee cannot reach the
security console, and — because separation of duties is the whole point — a
security analyst cannot use the employee portal either. An analyst who could
browse the customer book under the employee router would be performing the exact
access pattern this system exists to make visible.

## Safety constraints

These are properties of the system, not aspirations. Each is enforced in code
and covered by a test.

- **No secrets in telemetry.** Passwords, JWTs and API keys have no
  representation in `activities` or `audit_logs`, and the recorder has no
  parameter through which one could be passed.
- **Append-only security events.** Nothing in the application updates or deletes
  an activity, an audit entry or a risk score. Operator overrides append.
- **Backend-enforced authorisation.** Role is resolved from the database on every
  request, never from the token's claims.
- **Synthetic data only.** No real customer information exists in this
  repository.
